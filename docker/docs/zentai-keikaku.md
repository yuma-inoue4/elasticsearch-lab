# 全体計画（Docker Compose への移行）

## 1. 現在の状況と要件

### 業務上の目的

本番環境（Elastic Cloud）をトレース（再現）した試験環境を構築し、内部（Kibana、データフロー、アラート等）を作り込む。

### 現在の進捗

ラップトップ上に Multipass（VM 4台）を用意し、Ansible を使って環境構築自体は一度完了している。

### 扱うデータ・用途

最終的には、既存の本番環境で使われていない便利な機能（データライフサイクル最適化、インテリジェント・アラートなど）を社内に提案したい。

## 2. 直面している課題

### ブラックボックス化

環境構築の多くを AI に頼ったため、設定ファイルや Ansible タスクの裏側にある仕組みの理解が追いついていない。

### 複雑さ

VM 4台への直接インストール（セルフホスト）は、OS のカーネルパラメータ設定や TLS/SSL 証明書の手動管理など、泥臭いエラーが多く全体像が見えにくい。

### 作業環境の分散

構築は1人で行うが、Mac と Windows の両方の PC から作業を進めたい。

## 3. 【裏のテーマ】SRE 転職に向けたアピール材料

SRE への転職・キャリアアップにおいて、面接官に最も刺さるストーリーとして以下の3テーマを設定した。

1. **コスト最適化**  
   ILM（インデックス・ライフサイクル管理）と Searchable Snapshots によるストレージ費用の削減提案。

2. **トイル（手作業）の削減**  
   機械学習（異常検知）によるダイナミックアラートと、SLI/SLO の可視化。

3. **カオスエンジニアリング（障害テスト）**  
   ノードを意図的に落とし、クラスターの自動復旧やデータ再配置の挙動を検証。

## 4. 解決策：Docker Compose への移行

Multipass と Ansible の構成を一度横に置き、Docker Compose を用いた一元管理にシフトする。

### なぜ Docker か

- **圧倒的にシンプル**  
  何百行もの Ansible タスクが、1つの `docker-compose.yml`（約100行）にスッキリまとまり、ノード間の関係性が一目で理解できる。

- **データフローの全結合**  
  Elastic 本体と Kibana だけでなく、収集対象（Nginx など）やエージェント（Elastic Agent）まで1つのファイルで同時に起動・管理できる。

- **OS 不問（Mac / Windows 共通）**  
  同じ設定ファイルを Git で共有すれば、Mac でも Windows でも全く同じように動く。

- **障害テストが容易**  
  コマンド一つで特定のノードを即座に停止・再開できるため、SRE としての検証に最適。

## 5. 次の一手

環境を Docker ベースに切り替えるにあたり、まずは Mac と Windows のどちらでも動く **土台（Elastic 3ノード + Kibana）** を立ち上げる。

### 作業前に確認すること

1. 手元の Mac と Windows に Docker Desktop（または WSL2 上の Docker）はすでにインストールされているか。
2. 構築する Elasticsearch のバージョン（例: 8.15.0 など、本番に合わせるマイナーバージョン）の希望はあるか。

## 6. 作業の進め方（前回の反省）

Multipass / Ansible 期は、構築の多くを AI に任せた結果、**動くが理解が追いつかない（ブラックボックス化）** が課題になった。

そのため Docker 移行以降は次を原則とする。

- **AI には相談だけ行う**（方針・用語・詰まったときの切り分け・レビュー）
- **手を動かす・ファイルを書く・コマンドを実行するのは自分**
- 理解できない設定やコマンドは、そのまま採用せず、説明を聞いてから自分で反映する

面接・社内提案でも「自分が設計・構築した」と言い切れる状態を優先する。
