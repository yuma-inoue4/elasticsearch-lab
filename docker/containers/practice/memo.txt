--------------------------------------------------------------------------------
1. よく使うコマンド
--------------------------------------------------------------------------------

# 起動（フォアグラウンド。ログが見える。止めるときは Ctrl+C）
docker compose up

# 起動し直し＋イメージの再ビルド（compose / Dockerfile を変えたあと）
docker compose up --build

# 停止・削除
docker compose down
#   → コンテナと、この compose が作ったネットワークを削除する
#   → 名前付きボリューム（例: db-storage）は残る（DB のデータは消えない）

docker compose down -v
#   → 上記に加え、この compose が作った名前付きボリュームも削除する
#   → DB の中身も消えるので、初期化 SQL をやり直したいときに使う

# 動いているサービスの中に入る（compose 版の docker exec）
docker compose exec {サービス名} bash
# 例:
docker compose exec db bash

--------------------------------------------------------------------------------
2. ネットワーク（自動作成と名前解決）
--------------------------------------------------------------------------------

■ compose を up するとネットワークもできる
  - 自分で networks: を書かなくても、Docker がネットワークを作る
  - 名前の例: プロジェクト名_default（〇〇_default）
  - 同じ compose のサービス同士は、このネットワークでつながる

■ コンテナ間の名前解決（ホスト名でアクセス）
  - 「ユーザーが作成した（compose が作った）ネットワーク」上では、
    サービス名で互いに通信できる
  - 例: あるコンテナ内で
      curl http://my-nginx-2
    → 「Welcome to nginx!」のように応答が返る（相手のサービス名がホスト名になる）

■ 例外: デフォルトの bridge では名前解決が効かない
  - docker run だけしたときのデフォルト bridge では、
    コンテナ名での名前解決は（基本）できない
  - Compose で作った専用ネットワークだからサービス名で届く

--------------------------------------------------------------------------------
3. イメージとポート・環境変数
--------------------------------------------------------------------------------

■ イメージの「よくあるポート」はイメージごとに決まっている
  - 例: postgres ならコンテナ内は 5432、nginx なら 80 など
  - 確認方法: Docker Hub でイメージ名を検索し、ドキュメントを見る

■ イメージに「設定した方がよい環境変数」もある
  - 例: postgres の POSTGRES_PASSWORD / POSTGRES_USER / POSTGRES_DB
  - こちらも Docker Hub の説明を見る
  - compose の environment: に書く

■ ports の意味（おさらい）
  - 「ホスト側ポート:コンテナ側ポート」
  - 例: 5432:5432 → PC の 5432 から、コンテナ内の 5432 に届ける

--------------------------------------------------------------------------------
4. volumes（いちばん混乱しやすいところ）
--------------------------------------------------------------------------------

volumes を書く場所は 2 か所ある。役割が違う。

【A】ファイル末尾のトップレベル volumes:（全体）
  - 名前付きボリュームの「名前を登録（宣言）」する場所
  - 例:
      volumes:
        db-storage:
  - ここでは「ラベル（名前）だけ」。コンテナ内のパスは書かない

【B】各サービス内の volumes:（api や db の下）
  - 「その箱を、このコンテナのどのパスに付けるか」を書く場所（実態・代入）
  - 例（名前付きボリューム）:
      - db-storage:/var/lib/postgresql/data
        ↑名前（Aで宣言）  ↑コンテナ内のパス
  - 例（バインドマウント = ホストのフォルダを直接見せる）:
      - ./webapi/db/initdb:/docker-entrypoint-initdb.d
        ↑ホスト側（compose からの相対パス）  ↑コンテナ側（絶対パス）

使い分けの覚え方:
  - トップレベル … 「db-storage という箱を用意する」
  - サービス内   … 「その箱を /var/lib/postgresql/data にマウントする」
  - バインドマウント（./で始まるもの）はホストに実体があるので、
    トップレベルへの登録は不要

--------------------------------------------------------------------------------
5. DB の初期化 SQL をやり直すとき
--------------------------------------------------------------------------------

PostgreSQL 公式イメージの初期化スクリプト（/docker-entrypoint-initdb.d）は、
データディレクトリが空の「初回起動時」だけ実行される。

そのため:
  1. SQL やマウントパスを直した
  2. もう一度 init を走らせたい
のときは、ボリュームに古いデータが残っていると再実行されない。

手順の例:
  docker compose down -v    # 名前付きボリュームも消す
  docker compose up         # 初回扱いで init SQL が走る

注意:
  - down -v でも、バインドマウント元のホスト上のファイル（./webapi/db/initdb など）は消えない
  - 消えるのは Docker が管理する名前付きボリューム側

--------------------------------------------------------------------------------
6. compose を変えたあとにコンテナへ反映する
--------------------------------------------------------------------------------

Dockerfile やビルド内容を変えたとき:
  docker compose up --build

「設定だけ変えたのに古いコンテナのまま」と感じたら、
一度 down してから up、または up --build を試す。

--------------------------------------------------------------------------------
7. 用語の超短まとめ
--------------------------------------------------------------------------------

サービス … compose 上の1単位（api, db など）。だいたい1コンテナ
イメージ … コンテナのひな形（postgres:15 など）
ネットワーク … コンテナ同士をつなぐ仮想LAN（compose が自動作成しがち）
名前付きボリューム … Docker 管理の永続ディスク（例: db-storage）
バインドマウント … ホストのディレクトリをコンテナに直接マウント
名前解決 … サービス名（ホスト名）で相手コンテナに届くこと
